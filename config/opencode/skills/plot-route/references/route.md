# 按剧情路线指引修改相关内容

本流程把用户的**剧情路线指引**转化为结构化路线，在工程中逐节点取证定位，再按受控写入纪律执行修改。执行前先读取 `references/extract.md` 与 `references/rule.md`：路线涉及的实体必须先核对身份与关系，改名或新增名称必须遵守名称依赖协调。写入纪律、staging、注册流程以运行规则（`AGENTS.md`）为准，本文件不重复其细节，只描述剧情路线特有的判断。

## 第一步：路线结构化

把用户的路线指引拆成节点，每个节点必须填写下表字段。无法从指引中确定的字段标为 `未知`，禁止编造：

|字段|含义|工程锚点|
|---|---|---|
|地点|节点发生的地图或场景|地图名 / 地图 ID（`mapIndex`）|
|参与实体|该节点的角色、物品、技能|数据库条目 / 事件（`dbCatalog`）|
|触发条件|节点何时生效|开关 / 变量 / 自变量（`stateSlots`、`111` 条件分支）|
|内容|对白、演出、分支、战斗|事件页指令（`101/401/102/…`）|
|状态变化|节点改变的游戏状态|开关/变量赋值（`122` 等）、物品获得、成员增减|
|顺序依赖|该节点依赖或解锁的其他节点|前后节点的开关/变量链|

输出一份路线节点表，连同每节点的**待验证锚点**一起呈现给用户；锚点全部标 `未知` 且无法推断时，用 `question` 澄清路线意图，不要开始修改。

## 第二步：工程取证与定位

逐节点在工程中取证，每个节点必须找到至少一个证据位置才算"已定位"：

1. **实体核对**：路线提到的角色/物品/技能用 `dbCatalog`（query 过滤）核对是否存在。不存在时停下来用 `question` 区分：新建实体、用户笔误指向已有实体、还是路线超出当前工程范围。
2. **地图定位**：`action=mapIndex` 按名称找地图；`MapInfos.json` 与 `System.json` **禁止整读**，用 Grep 定位条目。
3. **事件定位**：`action=mapData`（offset/limit 分页）与 `action=eventContext` 读目标事件，确认该节点的对白与逻辑现状。
4. **状态链定位**：用 `stateSlots` 与 Grep 追踪开关/变量的赋值（`122`）与读取（`111`）位置，确认节点间的顺序依赖在工程里真实成立。链路断开（路线声称的先后顺序在工程中无状态支撑）时，在方案中列为需新增的状态节点，经用户确认后再改。
5. 取证结果记入路线节点表（证据位置列），并同步实体关系图——路线任务经常补充新的人物关系，按 `extract.md` 的判据收录。

## 第三步：变更方案分类

每个节点按修改类型选择对应写入通道，**一个节点可能包含多类变更**：

|变更类型|写入通道|约束|
|---|---|---|
|已有事件的对白/命令修改|`RmmvEvent` action=`patch.dryRun` → `patch.apply`；或受控直接编辑，必须留下 Git diff 等可审阅证据|首次编辑某 Map 文件前走 staging 快照；只改有证据定位的指令|
|数据库字段（名称、简介、技能、用语）|`RmmvDatabase` action=`validate` → `dryRun` → `stage`，再按流程应用|validate/dryRun 不写盘；对照表名白名单|
|新增事件|`RmmvEvent` action=`registry.register`（写满 `implementation.pages[].commands[]`）→ 预览决策 `question` → 用户在桌面画布人工放置|**禁止**用 `editor.update`/`editor.move` 写新事件 x/y；mapId 仅是建议|
|地图绘制/地形配合|`RmmvMap` paint 等动作|仅在用户明确要求地形配合时使用|
|名称统一或改名|先按 `rule.md` 名称依赖清单逐处协调，再走上述对应通道|比较值与显示位置必须同步，证据不足的位置列为未决并报告|

引擎边界：涉及插件指令时 MV 用 `356`（整串、空格敏感）、MZ 用 `357`（结构化参数 + `657` 显示）；以 `AGENT_RPG_ENGINE` 与任务前言为准，禁止混用。

## 第四步：执行与验收

- 按节点顺序执行变更；每完成一个节点，在路线节点表标记状态（`已改` / `待放置` / `受阻` / `未决`）。
- 受阻（工具报 critical diagnostics、证据冲突、状态链断裂）时 fail fast，向用户说明 blocker，不猜测补全。
- 全部节点处理完后做**路线一致性验收**：
  1. 每个节点的状态变化在工程中有对应的开关/变量/数据库落点；
  2. 节点顺序依赖与工程状态链一致（该开的开关会开、该判的分支会判）；
  3. 名称依赖协调完成：改过的名称在 `320`/`111`/`\N[n]`/脚本赋值各处一致；
  4. 控制符与占位符（`\N[n]`、`\V[n]`、`%1`）在改后的对白中完好。
- 验收发现缺口时回到第二步补充取证或更新方案。

## 收尾

- 向用户交付：路线节点表（含证据位置与执行状态）、变更摘要（哪些文件/事件/数据库条目改了什么）、未决事项。
- 把本次路线决策写入工程记忆（`RmmvMemory`）：type=`decision` 记录路线走向与状态链设计；新确认的人物关系按 `extract.md` 更新 character/convention topic。
- 后续会话继续这条路线时，先 `memory.list` / `memory.read` 读取既有路线与实体记忆，增量更新，不重建。
